# DigitalFace — manual SEO actions after deployment

Prepared 2026-09-05. Official website: **https://digitalface.app**. This task changed local source only. No Google, DNS, Vercel, GHL or n8n account setting was changed.

Follow these steps in order. Values marked **USER ACTION REQUIRED** must come from your own DigitalFace account; do not copy them from the Dra. Jennifer guide.

1. **Deploy the reviewed website source.** In the Vercel project connected to DigitalFace, confirm its repository/root points to the official DF Site source. The build command is `pnpm build:client`; output is `dist/spa`. Commit the reviewed source, generated public sitemap/robots and lockfile through your normal workflow, then deploy. Keep the private local .env out of the commit; its removal from Git tracking is intentional. Do not upload just index.html: all generated route documents and assets are required. Review Vercel dashboard overrides so they do not bypass this build or restore the old catch-all rewrite.

2. **Confirm the domain and redirects.** Open https://digitalface.app and https://digitalface.app/pricing. The www variant https://www.digitalface.app/pricing should permanently redirect to the same path on digitalface.app. HTTP should upgrade to HTTPS. Test /pricing/ and /pricing.html: both should end at /pricing. Test an existing URL with ?utm_source=seo_check: the page works and its canonical excludes the parameter. The local vercel.json supplies www/clean-URL rules; domain attachment, TLS, DNS and dashboard-level redirects remain external. Do not point all old or missing URLs at the homepage. If an owned older domain is being retired, inventory its actual URLs before planning a separate migration.

3. **Check the deployed HTML and error behavior.** Visit https://digitalface.app/es/pricing and use View Page Source: the initial title, description, canonical, lang=es, H1 and structured data should describe that Spanish page. Repeat for the homepage and all three industry URLs. Test https://digitalface.app/seo-check-nonexistent and https://digitalface.app/es/seo-check-nonexistent. They must return HTTP 404, carry noindex and have no canonical to a legitimate page. A visible error message with HTTP 200 is still a soft 404. Browser developer tools → Network shows the document status. For a terminal check, use `curl.exe -I https://digitalface.app/seo-check-nonexistent`. Public preview deployments must be protected or have a host-level noindex header; do not apply noindex to production.

4. **Perform your visual/conversion review.** Check phone, tablet and desktop layouts in English and Spanish, keyboard navigation, readable form errors, the language switch, FAQ/package expanders, the service shortlist and both website previews. All sections and conversion routes remain. This task intentionally did no visual automation. The existing booking provider is GoHighLevel, at /book and /es/book; do not add a second Calendly embed. Confirm the GHL widget works and speaks the appropriate language. Make a controlled synthetic contact submission and confirm receipt in your own approved workflow; this was not done live during the task. Ensure the server-side N8N_LEAD_WEBHOOK_URL remains configured in your hosting secret store.

5. **Create or select the Search Console Domain property.** Sign into the Google account that should own DigitalFace. Open [Google Search Console](https://search.google.com/search-console). In the property selector, choose Add property → Domain. Enter **digitalface.app**, without https:// or a path. If you already own that Domain property, use it instead of creating an unnecessary URL-prefix property. Property ownership/account access: **USER ACTION REQUIRED**.

6. **Verify ownership with DNS TXT.** Copy the exact TXT verification value Google generates for digitalface.app: **USER ACTION REQUIRED**. Add it at the authoritative DNS provider using a TXT record at the domain root (often host @). If DNS is managed somewhere other than Vercel, add it there. Do not use a token from another client or invent one. Return to Search Console and click Verify after the record resolves. Keep the TXT record afterward. See [Google's ownership-verification instructions](https://support.google.com/webmasters/answer/9008080).

7. **Submit the actual sitemap.** Open https://digitalface.app/sitemap.xml and https://digitalface.app/robots.txt after deployment. The sitemap should contain **24** URLs, all on https://digitalface.app, with English and Spanish equivalents. Robots should reference that same sitemap and allow crawling. In Search Console → Sitemaps, submit **https://digitalface.app/sitemap.xml**. Do not submit sitemap-index.xml from the old guide. If an old sitemap points at digitalfacemarketing.com, replace that submission with the correct sitemap for this property. XML without visual styling is normal. If Google reports an error, check its fetch/status details before changing code.

8. **Inspect priority URLs.** Use Search Console URL Inspection and Test live URL on https://digitalface.app/, https://digitalface.app/features, https://digitalface.app/pricing, https://digitalface.app/industries/dental-practices, https://digitalface.app/industries/aesthetic-medicine and https://digitalface.app/industries/med-spas. Repeat for their /es equivalents, and inspect /contact and /book. Confirm page fetch, crawl permission and canonical signals, then request indexing for priority pages where appropriate. Requesting indexing is not an indexing or ranking guarantee. Let the Sitemaps and Page indexing reports finish processing; do not repeatedly resubmit unchanged URLs every day.

9. **Create or select DigitalFace's GA4 property and web stream.** Open [Google Analytics](https://analytics.google.com/). In Admin, select the correct business-controlled property, then Data streams → Web. Use **https://digitalface.app** as the stream URL and a recognizable DigitalFace name. The Measurement ID begins with G-. Its actual value is **USER ACTION REQUIRED**. Do not reuse another client's ID or a numeric property/stream ID. If an existing DigitalFace tag is independently installed through GTM or Vercel settings, review it before enabling this direct integration.

10. **Review privacy and automatic measurement settings.** Before enabling analytics, confirm the site's disclosures and any needed visitor-consent mechanism for the markets you serve. The code has no consent banner or CMP and does not claim to provide a legal-compliance determination. In the GA4 web stream's Enhanced Measurement settings, open Page views → advanced settings and turn off **Page changes based on browser history events**; the code sends SPA page views itself and sets send_page_view:false for the initial Google config. Turn off automatic **Form interactions**, which can count attempts without server-confirmed success. Review site-search/outbound settings so arbitrary form or URL text is not collected. Do not configure a second automatic page_view or form-based generate_lead rule. Google Signals and ad-personalization signals are disabled by this code.

11. **Set the production environment variable and redeploy.** Vercel → the DigitalFace project → Settings → Environment Variables: add **VITE_GA4_MEASUREMENT_ID** with your real G- Measurement ID, scoped to **Production**. Redeploy production so Vite includes it in the browser build. No VITE_SITE_URL or SITE_URL override is needed: production SEO uses the fixed digitalface.app origin. Vercel supplies VERCEL_ENV automatically. If you intentionally build for another hosting provider, use DF_DEPLOY_ENV=production (Netlify's production CONTEXT is recognized). Both the production build flag and actual digitalface.app hostname are required, so local and preview traffic stay untracked. Do not add a copied gtag snippet or a second GTM tag to index.html.

12. **Verify GA4 Realtime with controlled visits.** Use a browser session where your chosen privacy/consent settings permit analytics and the tag is not blocked. Visit the homepage, a niche page, contact and pricing. Realtime/DebugView should show one page_view per path change, with the correct title and language. A fragment jump or changing ?from= on the same path should not create another page view. Click a consultation link: consultation_click means the person opened the booking flow. Click the existing sales email: contact_click records the method without copying the email address. Add a service: service_request_add should appear. Complete one approved synthetic form submission: generate_lead should appear only after the success message. In the tag/network inspection, confirm one gtag.js loader and your own Measurement ID. The task's tests simulated these events offline; actual Google ingestion is **USER ACTION REQUIRED**.

13. **Choose meaningful GA4 Key Events.** In Admin → Events/Key events, find **generate_lead** and mark it as a Key Event. This is the primary completed website inquiry. Its lead_type differentiates contact from service_request. Optionally register the event-scoped custom dimensions **lead_type**, **page_source**, **locale**, **service_id** and **contact_method**, and custom metric **service_count**, if useful for reporting. Keep page_view and service_request_add as diagnostics. Treat consultation_click and contact_click as secondary intent, not qualified leads or booked appointments. Do not sum service-request leads and all generate_lead events as separate conversions; the former are a subset of the latter.

14. **Confirm the booking/qualification measurement contract.** A loaded iframe, selected slot, resized calendar or consultation_click does not prove a booking. The current code does not emit a fake booked-consultation event. A future confirmed-booking event must come from a documented, validated GHL completion signal or an approved server-side workflow, include a deduplication design and exclude contact details from GA4. Qualified lead and revenue reporting also require CRM-side definitions and confirmed outcomes. Provider configuration and identifiers for that separate integration are **USER ACTION REQUIRED**.

15. **Link Search Console to GA4.** In GA4 Admin → Product links → Search Console links, link the verified **digitalface.app** Domain property to the **https://digitalface.app** web stream. Use an account with access to both. Publish the Search Console report collection in Analytics if your reporting workspace requires it. This allows search-query/landing-page reporting alongside acquisition data. See [Google's linking guide](https://support.google.com/analytics/answer/10737381).

16. **Verify business identity before local listings.** Reconcile the website's sales email, Cali address, Florida remote-service wording, company identity and official social-profile URLs. Do not create a Miami street address or virtual office claim. Google Business Profile requires eligibility; an online-only business is not eligible merely because it serves Florida remotely. If DigitalFace genuinely meets the in-person/service-area requirements, claim or update the eligible profile with accurate information and https://digitalface.app. Eligibility, category, address/service area and account access are **USER ACTION REQUIRED**. Use [Google's eligibility rules](https://support.google.com/business/answer/13763036), not the existence of website schema as proof.

17. **Set up Bing and legitimate references.** In [Bing Webmaster Tools](https://www.bing.com/webmasters/), add the verified site or use its Search Console import option if available to your account. Submit https://digitalface.app/sitemap.xml. Add consistent website links to legitimate company/social profiles and relevant industry directories. Ask clients for permission to reference completed work and for honest reviews on platforms where the business is eligible. Do not buy links, fabricate reviews or create duplicate listings to simulate local offices.

18. **Approve the next content and commercial updates.** Reconcile the current website's Capture / AI / Sales System scope with the older approved Capture / AI / Full Growth fees recorded in PROJECT_CONTEXT.md under D:/Desktop/DF; this SEO pass did not assume a new price approval. Resolve the conflicting included-AI-credit wording before relying on it in sales. Prioritize substantive Jennifer/Diego case studies with client permission, then one differentiated AI/CRM or paid-ad service page. Use actual project scope and evidence; never invent results. Keep English/Spanish parity. After any new route, update shared/site.json and its component mapping, run the build, and review the regenerated sitemap and metadata. The prioritized plan is in SEO_IMPLEMENTATION_REPORT.md.

19. **Monitor monthly.** In Search Console review clicks, impressions, queries, landing pages, country, language and indexing exclusions. In GA4 compare Organic Search landing pages, generate_lead rate and lead type; use your CRM to determine which accepted submissions became qualified opportunities. Review Core Web Vitals when enough real-user data exists. Check broken links, 404s, forms, calendar loading and language parity. Annotate deployment/content dates so you can distinguish changes from seasonality. No forecast of traffic or lead volume is justified before this baseline exists.

20. **Finish the configuration-history cleanup.** The existing .env is preserved locally but is staged for removal from Git tracking. .env.example contains names only, with empty values. Review prior repository exposure; rotate/revoke any affected live credentials or private endpoints as appropriate. Plan history cleanup with repository owners if needed. Do not paste values into this checklist, reports or chat. This task neither rewrote history nor rotated credentials.
