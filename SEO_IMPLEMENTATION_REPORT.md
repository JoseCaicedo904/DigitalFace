# DigitalFace SEO implementation report

Date: 2026-09-05 (America/New*York). Scope: the official website source at `C:/Users/jose*/OneDrive/Documents/WEBSITES/Website Official DF/DF Site`. Canonical origin: https://digitalface.app.

## A. Executive summary

The existing site had localized, route-specific metadata hooks, but they ran only in the browser. Every public URL initially received the same homepage HTML shell, canonicalized to the old digitalfacemarketing.com host. The sitemap and robots file used that old host too. Vercel rewrote every unknown path to index.html, creating HTTP 200 soft 404s. Its configured build ran only Vite and bypassed sitemap generation. There was no GA4 installation.

The implementation preserves React 18, Vite and React Router 6, the corporate sections, three industry funnels, service request builder, forms and the existing GoHighLevel booking page. It generates real route content, localized metadata and structured data at build time, then hydrates those same components for interaction. All 24 existing indexable URLs were reviewed and optimized: 12 English and 12 Spanish. No thin service, city, blog or case-study pages were published.

The source now uses one production origin and one route registry. Unknown direct requests receive a real 404 through the local production server; Vercel configuration removes the catch-all rewrite and uses its native custom-404 handling. GA4 is ready for a user-supplied Measurement ID and counts a lead only after the form endpoint confirms success.

**Evidence boundaries:** public HTTP requests were read-only. The live baseline in `seo-audit/live-http-baseline.json` tested 29 visitor-style URLs and 26 crawler-style requests (24 public routes plus two nonexistent routes). All 26 crawler-style requests returned HTTP 200 with one shared initial title and zero H1s. Changing a User-Agent is a diagnostic probe, not a real Google crawl or Search Console validation. HTTP and www redirects already returned 308 in the tested samples. Nothing was deployed, no DNS/account settings were changed, and no form, calendar or provider API was submitted live.

The two attached guides were treated as references, not operational instructions. No other client's analytics ID, DNS token, domain or schema was copied.

## C. Technical SEO changes

### Rendering, metadata and languages

- `shared/site.json` supplies the fixed https://digitalface.app origin, real routes, intent, indexability and page type. Router registration, prerendering, sitemap and validation consume it.
- `client/entry-server.tsx` uses React's server renderer and waits for lazy route content. No browser, screenshot tool or production data service is involved. `scripts/prerender.mjs` produces index.html, es.html, the other 22 route documents and two error documents under dist/spa.
- `usePageMetadata` collects each page's existing localized copy during rendering. `client/lib/seo.tsx` uses it for initial HTML and subsequent client navigation. This avoids a second, drifting metadata dictionary.
- Canonicals are self-referencing, absolute, non-www HTTPS URLs. Queries and fragments are omitted. Spanish alternates point to matching Spanish content, never a generic homepage. All pairs include reciprocal en/es/x-default references in HTML and sitemap.
- Error pages have no canonical, hreflang or page/company schema. Their initial HTML carries noindex, follow. Navigating back to a valid route replaces the error directive correctly.
- Storage restoration is deferred with a React transition so it neither overwrites saved requests nor interrupts hydration of lazy routes. Non-visual hydration tests cover ten representative documents across both languages, industry and corporate layouts, forms, catalog, booking and legal content.
- The existing locale detection rules remain. Unknown URLs bypass locale redirection so they reach the 404 handler. Locale guesses are temporary, uncacheable redirects; crawler exceptions and explicit /es paths are preserved. This automatic language behavior remains a future UX consideration, not a new SEO tactic.

### Sitemap, robots, hosting and redirects

The build now always generates https://digitalface.app/sitemap.xml and https://digitalface.app/robots.txt before compiling. The sitemap includes exactly 24 canonical indexable URLs, excludes errors and parameters, and supplies paired language alternates. Build time is not used as a fabricated page-modification date; lastmod, changefreq and priority are omitted.

Robots allows crawling and references the production sitemap. Vercel uses clean URLs without trailing slashes, the www-to-apex permanent redirect and the existing API rewrite. The previous universal /index.html rewrite was removed. Its native 404.html serves unknown URLs. The Express production entry was repaired for Express 5 and shares a tested static-file/route handler. Direct pages, trailing-slash/HTML normalization, XML/robots MIME types and unknown page/asset/API status codes are tested locally. Netlify's existing build command now uses the same complete client build; its production routing was not deployed or verified.

No legacy page redirect was invented without evidence of a real retired URL. If Search Console or hosting logs later identify an old URL, map it directly to the closest relevant replacement, with no blanket homepage redirects. The user must review domain-level redirects and any overrides configured in the hosting dashboard; combined host/path variants may pass through both domain and clean-URL normalization.

### Structured data

Organization and WebSite remain the site-level entities; the WebSite has one stable root URL and both languages. Each route now adds a WebPage subtype (AboutPage, ContactPage or CollectionPage where appropriate), a stable page ID and BreadcrumbList for non-home routes. Service entities describe the actual system, catalog and three industry offers, linked to https://digitalface.app/#organization. Florida is represented as a service area, with matching visible remote-service copy.

Industry FAQs use the same questions and answers as their accessible expandable UI. All answers and package descriptions now remain in the DOM while closed. FAQ markup describes the content; it does not establish eligibility for Google FAQ rich results. DigitalFace is an agency, not a medical provider. Duplicate industry breadcrumb blocks were removed. No ratings, reviews, awards, fabricated addresses, credentials, employees, outcomes, Offer prices or unsupported Article/Person entities were added.

The existing Cali address and published sales email remain unchanged. An email on digitalfacemarketing.com is not a website canonical URL and was deliberately preserved. Business ownership, address validity and official social-profile URLs require owner confirmation; no sameAs links were guessed.

### Content, semantics, media and performance

The homepage title now names customer acquisition and marketing automation, and its concise hero/description truthfully introduces Florida/US/LATAM coverage. It retains the broader appointment-driven-business context found in the current source. The three existing niche pages retain distinct dental inquiry, aesthetic consultation and med-spa retention language. Contact gets an explicit business-inquiry H1. The system overview and pricing intro no longer skip from H1 to H3. Existing design classes remain.

All checked internal links and fragment targets exist, and no page is orphaned. Navigation and CTAs use real anchors/React Router Links. Existing parent/sibling links are preserved; industry footers include concise bilingual remote service-area copy. Forms keep associated labels, error messages, field IDs and their existing backend contract.

Two broken case-study image paths now use the existing published client website previews. No portrait or result was invented. Their original PNGs remain intact. New WebP derivatives preserve dimensions: Jennifer 844,798 → 102,830 bytes; Diego 1,073,563 → 97,624 bytes, an approximately 89.6% combined reduction. Spanish media-slot alt text now matches the page language. Decorative images remain empty-alt; contained media retains fixed aspect-ratio sizing, and below-fold images use lazy loading. The existing 1536×1024 social image is retained; a future owner-approved 1200×630 export can improve crop consistency.

All public pages are route-split, including the homepage. During this pass, the initial JS entry decreased from approximately 846 KB to 556 KB minified (252 KB to 167 KB gzip); these are local build comparisons, not field-performance measurements. The booking widget remains confined to /book and /es/book. Fonts use one stylesheet request with preconnect and display=swap instead of chained CSS imports. The hero video uses metadata preload and retains its poster, playback and layout. A no-JavaScript fallback exposes animation-hidden content without changing normal animations.

The shared bundle is still substantial, and an autoplay hero video can consume bandwidth despite metadata preload. No Core Web Vitals score or visual quality improvement is claimed. Field performance, animation smoothness, mobile layout and final image crops require the user's post-deploy review.

## F. Conversion measurement

Configure **VITE_GA4_MEASUREMENT_ID** with the ID generated by DigitalFace's GA4 web stream. **USER ACTION REQUIRED.** No Measurement ID is hardcoded. Vercel builds expose VERCEL_ENV to the code; only a production build/deployment on the exact digitalface.app hostname initializes GA4. Preview deployments and localhost stay untracked even if an ID is accidentally configured. A non-Vercel production build must explicitly supply DF_DEPLOY_ENV=production; Netlify production CONTEXT is also recognized.

| Event               | Actual trigger                                                                      | Parameters                                                                                         | Key Event recommendation                         |
| ------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| page_view           | First resolved route and subsequent path changes, after the localized title applies | page_path, page_location, page_title, page_referrer, locale                                        | No                                               |
| generate_lead       | POST /api/lead returns both HTTP success and JSON ok:true                           | page_source, lead_type=contact or service_request, service_count, page_path, page_location, locale | Yes: primary website lead outcome                |
| consultation_click  | A real link to /book or /es/book is activated                                       | page_path, page_location, locale                                                                   | Secondary intent only; not a booked consultation |
| contact_click       | Existing email link, or a phone/WhatsApp link if used by the site                   | contact_method, page_path, page_location, locale                                                   | Optional secondary intent                        |
| service_request_add | An unselected catalog service is added                                              | service_id, page_path, page_location, locale                                                       | No; diagnostic shortlist activity                |

One Google script loader is used; direct config disables automatic initial page_view and duplicate same-path calls are suppressed. A pre-existing independent tag is left alone rather than duplicated. **Disable GA4 Enhanced Measurement browser-history page views and form interactions for this custom measurement setup. The code already disables the automatic initial config page view.** Otherwise account-side automatic events may duplicate navigation or count a form before the backend accepts it. Do not install the same stream through GTM as well.

The tag receives known route paths and a fixed parameter whitelist, never form values, names, emails, messages, arbitrary unknown paths, query strings or fragments. Referrers are reduced to safe known site paths or external origins. Google Signals/ad personalization are disabled in this integration. The existing first-touch UTM/referrer data sent through the private form contract is preserved separately. Since the GA4 URL is sanitized, campaign query data is not explicitly forwarded by this layer; validate paid-campaign attribution separately rather than expecting full campaign fidelity. Organic acquisition should still be reviewed using search referrers and linked Search Console.

A successful API response confirms acceptance by the website's upstream workflow, not a qualified lead, completed CRM automation or paid sale. Cross-origin calendar height/load messages are **not** treated as a booking. Confirmed appointments need a documented GHL calendar completion or server-side booking event, deduplicated and tested separately. No invented appointment_booked event was added. The four form regression cases verify success and HTTP, application and network failure behavior with synthetic data and mocked transport.

## I. Remaining risks, validation and rollback

### Business/content risks requiring owner decisions

1. **Pricing is inconsistent with the durable DF briefing.** That briefing approves Capture $597 setup + $790/month, AI $1,097 + $1,200/month and Full Growth $1,597 + $1,800/month. The actual website uses a newer-looking Capture / AI / The DigitalFace Sales System presentation and does not render those package fee amounts. Existing visible usage-credit language also conflicts with newer no-included-credit wording. This SEO pass preserves the current commercial presentation and does not infer a new price approval or add Offer prices to schema. Reconcile the offer across pricing, industry funnels and FAQs in a dedicated owner-approved commercial edit.
2. The published Cali address, Miami remote-service wording, response-time claims, ownership guarantees and client proof need owner verification. No account/admin records or private client material were used as proof. Existing claims were not amplified into ratings or results.
3. Actual customer qualification, booked consultations, CRM success and revenue cannot be inferred from a contact-form acceptance or calendar click. Complete the external conversion contract before reporting those outcomes.
4. Consent choices and the published privacy/cookie disclosures need an owner-approved implementation for the markets served before enabling measurement where consent is required. This task prepares a direct tag, not a CMP or legal determination. No new consent banner was added to the design.
5. A valid sitemap, schema and crawlable HTML do not guarantee indexing, snippets, rich results or rankings. No GSC, analytics history, backlink data or keyword-volume dataset was available.

### Security and technical boundaries

The repository already tracked .env. Tracking was removed with git rm --cached; the local file was preserved and ignore rules now cover environment variants with only .env.example allowed. The index contains that deliberate removal; other source changes remain uncommitted. Existing Git history may still contain restricted configuration. The owner must review exposure, rotate/revoke any affected live secrets or private endpoints as appropriate and manage history cleanup separately. No secret value was printed, copied into a report or used to contact a private endpoint.

Client form/CRM contracts, server-side destination configuration, selected-service IDs, language routes, client site URLs and booking calendar configuration remain intact. No n8n, CRM or calendar mutation was made. API and preview behavior on hosting must be confirmed after deploy. A nonproduction Vercel preview may need protection or a host-level noindex header; production canonicals alone do not make a public preview private.
